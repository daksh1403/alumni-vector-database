# Alumni Vector Database

I built this DBMS mini project to help students find alumni, mentoring and jobs through natural-language search. It includes a responsive website, a Cloudflare Worker API and a Qdrant database.

[Open the website](https://alumni-vector-console.dakshx.workers.dev/)

## Features

- Search Alumni, Mentoring or Jobs and explore up to five relevant matches.
- Filter by department, skill, location and record source.
- Browse additional records, open details and follow stored connections.
- Add, edit and delete records using a private admin token.
- Use the website on desktop or mobile, with optional animations.

## How it works

`Website → Cloudflare Worker → Qdrant → Search results`

1. Record titles, descriptions and skills are converted into 384-dimensional MiniLM vectors.
2. A search combines semantic similarity with BM25 keyword matching and applies the selected filters.
3. Reciprocal Rank Fusion combines both rankings and returns up to five matches.

Qdrant stores the original record details alongside the vectors. Saving an edited record regenerates its vectors. Descriptions are entered by the admin or created from seed templates, not generated by a chatbot.

**Stack:** HTML, CSS, JavaScript, Cloudflare Workers, Qdrant Cloud, MiniLM, BM25 and Wrangler. No JDBC is used.

## Data

The deployed collection contains 101 records: **50 alumni, 20 jobs, 15 mentoring records and 16 supporting records**. Counts can change through admin operations.

There are 22 records migrated from the earlier Neo4j project and 79 generated sample records. Alumni names are unique, mentoring titles identify their learning track, and batch labels include department and section where available. The 33 migrated relationships are stored as record references.

Sample records are labelled **Sample**. They are not verified alumni profiles or job openings. A fresh seed without the private migration file creates 85 sample records. Qdrant performs real retrieval over this data.

## Local setup

Requires **Node.js 22+**, npm and a Qdrant Cloud cluster with access to the configured inference models.

```sh
git clone https://github.com/daksh1403/alumni-vector-database.git
cd alumni-vector-database
npm ci
cp .env.example .dev.vars
```

Edit `.dev.vars` with your own values:

```dotenv
QDRANT_URL=https://your-cluster.cloud.qdrant.io
QDRANT_API_KEY=your-database-api-key
VECTOR_ADMIN_TOKEN=your-long-random-admin-token
```

Then run:

```sh
npm run seed
npm run dev
```

Open the URL printed by Wrangler. It serves both the website and API. On Windows PowerShell, use `Copy-Item .env.example .dev.vars` instead of `cp`.

The collection and model are configured in `wrangler.jsonc`. Seeding uses stable IDs, but it can overwrite edits to seeded records. Private migration files and credentials are excluded from Git.

## Deploy

Use your own Worker name in `wrangler.jsonc` when creating a separate deployment.

```sh
npm exec -- wrangler login
npm exec -- wrangler secret put QDRANT_URL
npm exec -- wrangler secret put QDRANT_API_KEY
npm exec -- wrangler secret put VECTOR_ADMIN_TOKEN
npm run deploy
```

This deploys the complete frontend and backend. GitHub pushes run checks but do not automatically deploy the website. Keep keys in local configuration or Cloudflare secrets, never in frontend code.

## Tests

```sh
npm exec -- playwright install chromium
npm run check
```

This runs backend tests, browser tests and a deployment dry run. Browser tests use controlled API responses without cloud credentials. Run `npm run evaluate` separately to check search relevance against your configured Qdrant collection.

If the website shows Unavailable, check `.dev.vars`, cluster access and `/api/health`. Passing local tests does not establish live database connectivity.

## API

| Method      | Endpoint                             | Purpose                   |
| ----------- | ------------------------------------ | ------------------------- |
| GET         | `/api/health`                        | Database connectivity     |
| GET         | `/api/stats`, `/api/facets`          | Counts and filter values  |
| POST        | `/api/search`                        | Hybrid search             |
| GET         | `/api/records`, `/api/records/:uuid` | Browse or read a record   |
| POST        | `/api/records`                       | Create a record           |
| PUT, DELETE | `/api/records/:uuid`                 | Update or delete a record |

Search accepts JSON such as `{"query":"Python project mentor","kind":"alumni"}`. Browse responses include a `nextOffset` for pagination. Writes require `Authorization: Bearer <VECTOR_ADMIN_TOKEN>`. Record descriptions must contain 20 to 4000 characters.

## Current scope

The project searches its stored collection, not the internet. It provides discovery and record management, with no messaging, applications, booking or student sign-in. Graph connections are metadata references rather than native graph traversals. Read endpoints are public, including migrated source properties, so imported data must be suitable for public display.
